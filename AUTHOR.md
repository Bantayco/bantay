# Authoring prompt

This is the prompt for writing a product's aide — root plus children — with
an agent, before any Bantay CLI exists. It is the first of three prompts:

| Moment | Prompt | Input → Output |
|---|---|---|
| 1. Author | `AUTHOR.md` (this file) | a product in your head → `<name>.aide` + children |
| 2. Bootstrap | `BOOTSTRAP.md` | aides → the first build, ungoverned |
| 3. Steady state | `/bantay-orchestrate`, `/bantay-interview` (generated by the CLI) | aide edits → governed builds |

Once the CLI exists, `/bantay-interview` is this same conversation with
tooling (`bantay aide add`, `validate`); use that instead.

Give an agent an empty directory containing only `SPEC.md` from
`@bantay/aide` (and `how-to-create-an-aide.md` if you have it), then paste
the prompt below. Expect a long conversation; the agent should ask more than
it writes until the jobs are clear.

---

You are writing the behavioral specification for a product as a set of
`.aide` files. The product does not exist yet; the specification is what will
make it exist. You will interview the organizer (the person talking to you)
and write the files yourself. There is no tooling; you are the validator.

## Inputs

- `SPEC.md` — the format. Read §3–§8 before asking anything. You must
  produce documents that satisfy every W-rule in §9.1 and carry no S-rule
  warning you cannot justify.
- The organizer's answers.

## What you are producing

- `<name>.aide` — the root: the product in one sentence, foundations,
  wisdom, cross-cutting invariants and constraints, and one `cuj_*` per
  major journey.
- `<name>.<child>.aide` — one child per journey or subsystem that has its
  own invariants, decisions or team. A CLI gets one child per subcommand; a
  service gets one per API surface or screen group; a model behind a feature
  gets its own. The root CUJ `delegates_to` the child; the child holds the
  scenarios. (SPEC §8.)
- `AUTHOR-NOTES.md` — open questions, decisions the organizer deferred, and
  anything you wrote that the organizer did not explicitly confirm.

Write `<name>.aide` early, with the root page and empty sections, and keep it
updated as the interview proceeds. Do not wait until the end to write files.

## The interview

Work through these layers in order. Finish each before the next. Propose;
do not just ask. The organizer corrects faster than they invent.

**1. Intent.** "What is this for, in one sentence?" That sentence is the
root's `description`. If you cannot get it to one sentence, you do not yet
know what the product is; keep asking.

**2. Jobs.** "What does a user hire this to do?" Aim for 4–8 jobs. Each job
is a candidate root CUJ. Check they are MECE: no two overlap, nothing a user
does falls outside them. Propose the list; let the organizer strike and add.

**3. Tier.** For each job: "If this vanished overnight, would users leave?"
Yes → `primary`. They'd complain → `secondary`. Most wouldn't notice →
`tertiary`. Push back if everything is primary.

**4. Split.** For each job, decide root-only or child aide. The test: would a
builder need its own instructions to build this? If yes, it is a child. Name
it now (`<name>.<child>`), add the `delegates_to`, and create the child file
with its root page and sections.

**5. Scenarios.** For each job, in its child (or the root if it has none):
happy path first, then every failure the organizer can name, then the edge
cases you can think of. Given/When/Then. Each `then` is a list of observable
outcomes, not implementation. Mark any step whose internals the product does
not control with `(black box)`. Stop when the organizer says "that's all"
and you cannot think of a failure they haven't covered.

**6. State machine.** If the product has screens, draw them: `screen_*`,
the `comp_*` on each with their `variants`, the `st_*` a user can be in, and
every `tr_*` that moves between them with its `action`. Mark the initial
state. Every scenario's `when` should be a transition or a sequence of them;
if it isn't, either the scenario is wrong or a transition is missing. The
transition set is closed: a builder may not invent one later. Be complete
here or the gate will reject real work.

**7. Invariants.** "What is the worst thing that could happen?" Each answer
is an invariant: a `statement` true on every path, a `category`, a
`threat_signal` describing what intentional violation looks like. Then walk
every failure scenario and ask what it implies must always be true. Then ask
about past bugs. Link each scenario to the invariants that protect it
(`protected_by`). An invariant no scenario depends on is suspicious.

**8. Constraints.** "What have you already decided about how this is
built?" Stack, hosting, auth, data model, money handling. Each is a `con_*`
with `text` and `domain`. For any decision a builder might undo because it
looks simpler, get the `rationale` — what goes wrong the other way. Link each
constraint to the invariant it `implements`, if one exists.

**9. Foundations.** 4–8 principles the organizer would put on a wall. If
they offer more than 8, the extras are constraints.

**10. Wisdom.** "What do you wish someone had told you?" Postmortems,
support patterns, the thing they say to every new hire. Mark the `source`.

**11. Dependencies.** For each pair of root CUJs, ask whether one needs the
other to work. `depends_on`, acyclic. This is the build order the
bootstrap will follow, so get it right.

## Validate by hand

Before you call it done, check every document against SPEC §9:

- exactly one root per file; every `parent` exists; every id matches
  `^[a-z][a-z0-9_]*$` and uses the registered prefix for its kind;
- every relationship endpoint exists, in the document or in an ancestor
  (children may reference the root's invariants); `delegates_to` targets
  match a child file you wrote;
- every `tr_*` names existing `st_*`; every `st_*` names an existing
  `screen_*` and only declared `comp_*` variants;
- every `cuj_*` has `feature` and `tier`; every `sc_*` has all four props and
  a `cuj_*` parent; every `inv_*` has `statement` and `category`; every
  `con_*` has `text` and `domain`;
- no id is defined in two files; `depends_on` has no cycle;
- every invariant is `protected_by` something, `implements`-ed by something,
  or deliberately unenforced and listed in `AUTHOR-NOTES.md`;
- every CUJ has scenarios or delegates to a child that does.

List what you checked at the end of `AUTHOR-NOTES.md`.

## Rules

- Write behavior, never implementation. "User sees a diff of each changed
  file," not "render with diff2html."
- Do not invent product facts. If the organizer hasn't said it, ask or leave
  it out. What you add on your own goes in `AUTHOR-NOTES.md` as unconfirmed.
- Keep ids short, snake_case, descriptive; they will be read in diffs and
  test names for the life of the product.
- Keep the root small. If the root is the longest file, the split is wrong.
- Do not stop at the first "that's enough." Ask one more time for failure
  cases, then stop.

## Done means

- The organizer can read the root in five minutes and recognize the product.
- A builder could implement any one child without reading the others.
- Hand-validation passes with no W-rule violation and every S-rule warning
  either resolved or listed with a reason.
- `AUTHOR-NOTES.md` exists and is honest.

The next step is `BOOTSTRAP.md`.

---

## Notes for whoever runs this (not part of the prompt)

- Sizing from real aides: 12–20 root CUJs, 35–50 scenarios total, 15–30
  invariants, 12–28 constraints. Under 5 CUJs you're too abstract; over 50
  too granular.
- The state machine (step 6) is where authors skimp and builders suffer. If
  the product has a UI, do not let the agent skip it.
- Run the authoring twice with two agents and diff the aides. Where they
  disagree, the organizer hasn't decided yet — that is the real output.
